# Архитектура Sigma RuleForge

## Статус и границы

Это проект архитектуры. Все компоненты ниже предстоит реализовать. MVP работает локально и офлайн: читает правила и синтетические fixtures, выдаёт диагностику и текст запросов. Он не выполняет запросы, не запускает содержимое правил и не подключается к production SIEM.

## Компоненты

| Компонент | Ответственность | Результат |
| --- | --- | --- |
| YAML loader | Безопасная загрузка UTF-8 и позиции узлов | Документ с source map |
| Validator | Структура, типы, condition, профиль поддержки | Валидированное правило или диагностика |
| IR builder | Нормализация без изменения логики | Дерево предикатов и метаданные |
| Field pipeline | Явный mapping logsource и полей | IR для выбранной схемы событий |
| Backend adapter | Проверка возможностей и генерация | Запрос, версия backend, диагностика |
| ATT&CK resolver | Проверка тегов по локальному snapshot | Связи и предупреждения |
| Test harness | Golden-проверки и поведенческие fixtures | Детерминированный отчёт |
| CLI | Аргументы, пакетная обработка, формат вывода | stdout/stderr и exit code |

## Sigma YAML-парсер

Использовать безопасный loader без создания произвольных объектов, custom tags и выполнения кода. Запрещать повторяющиеся ключи, recursive aliases и неконтролируемое расширение anchors; для MVP предлагается отклонять anchors/aliases полностью. Ввести лимиты размера файла, числа узлов, глубины и длины строк до затратной обработки. Значения лимитов и профиль совместимости публикуются с реализацией.

MVP принимает один detection rule на YAML-документ. Multi-document YAML, correlation rules и filters отклоняются с явной диагностикой до появления поддержки. Это ограничения RuleForge, а не всей спецификации Sigma. Сохранять имя файла, строку и колонку для структурных и семантических ошибок.

## Валидация

Проверка делится на синтаксическую, структурную и семантическую. Проверять обязательные поля выбранной версии спецификации и отдельно требования профиля RuleForge. Для публикуемых правил проект требует title, UUID id, logsource, detection и condition; этот профиль может быть строже спецификации.

Проверять типы metadata, корректность UUID, дубликаты id в пакете, допустимые значения status/level, структуру logsource и selectors. Не удалять неизвестные метаданные молча: сохранять их и выдавать предупреждение. Формировать condition AST с приоритетами, скобками, and/or/not и разрешением имён selectors. Поддержку `1 of`/`all of`, wildcard selectors и modifiers включать только после появления тестов. Неизвестный selector и неподдержанный modifier — ошибка; отсутствие field mapping запрещает конвертацию в строгом режиме.

## IR и конвертация

IR содержит metadata, logsource, дерево условий и типизированные значения с ссылками на исходные позиции. Отличать строки, числа, bool и null. Семантика списков, wildcard, escaping, отрицаний, отсутствующих полей и регистрозависимости должна быть описана и протестирована. Нормализация не меняет оригинальный файл.

Конвертер сначала проверяет capabilities адаптера, затем применяет версионированный field pipeline и генерирует запрос. Любая потеря семантики — ошибка, а не частичный успешный запрос. Не применять eval, shell interpolation или плагины из входного YAML.

## Backend-адаптеры

Каждый адаптер предоставляет name, version, поддержанные logsource/modifiers/operators и методы проверки совместимости и генерации. Выходной manifest включает rule id, hash входа, target, pipeline version, версию спецификации и инструмента. Не включать абсолютные локальные пути и сырые события в публичные отчёты.

| Backend | Планируемый формат | Статус |
| --- | --- | --- |
| Splunk | SPL | Первый кандидат MVP |
| Elastic | Формат будет выбран явно: Lucene или EQL | После MVP |
| QRadar | AQL | После MVP |

Конкретный dialect/version является частью контракта: нельзя считать форматы одного SIEM взаимозаменяемыми. Конфигурация mapping — локальный проверяемый файл; сетевые credentials не нужны. Возможность использования pySigma оценивается отдельно, с фиксацией зависимостей и лицензий.

## Golden-наборы

Планируемые каталоги: `tests/fixtures/rules/`, `tests/fixtures/events/`, `tests/golden/<backend>/` и `tests/manifests/`. Сейчас их нет. Manifest связывает вход, ожидаемую диагностику или запрос, версии pipeline/backend и ожидаемые совпадения событий.

Положительные случаи: базовые selectors, вложенные условия, строки с escaping, поддержанные modifiers. Отрицательные: повреждённый YAML, повтор ключей/id, неизвестные selectors, чрезмерная глубина, unsupported features и отсутствующий mapping. Для каждого backend проверять quoting, null/missing fields, списки, case sensitivity и negation.

Golden diff проверяет стабильность текста, но не эквивалентность логики. Отдельные поведенческие тесты используют только синтетические события с явно заданными matches/non-matches. SIEM integration tests — отдельный добровольный этап в авторизованной лаборатории. Изменение golden требует ручного review; слепое обновление snapshots запрещено.

## MITRE ATT&CK mapping

Разбирать теги `attack.tXXXX` и `attack.tXXXX.XXX`, нормализовать регистр и сопоставлять идентификаторы с локальным версионированным ATT&CK STIX snapshot. Сохранять domain, release/version, provenance URL и digest snapshot. Runtime-загрузка из сети не нужна; обновление datasets выполняется отдельным проверяемым шагом с сохранением условий использования.

Неизвестные, deprecated или revoked IDs должны давать отдельную диагностику. Техники и подтехники не смешиваются; tactics сверяются с snapshot. Тег автора — заявленная связь, а не доказательство детектирования. Отчёт различает количество mapped правил и подтверждённые синтетическими тестами случаи; процент покрытия ATT&CK не заявляется без определённого знаменателя и методики.

## Обработка ошибок

Планируемый формат диагностики: `code`, `severity`, относительный `file`, `line`, `column`, `rule_id`, `message`, `hint`. Координаты могут отсутствовать для ошибок IO или backend. Не печатать сырые значения, события и traceback по умолчанию.

| Код группы | Смысл |
| --- | --- |
| YAML_* | Синтаксис, дубликаты ключей, unsafe tags, лимиты |
| SCHEMA_* | Неверные поля, типы и метаданные |
| CONDITION_* | Неизвестные selectors или некорректное выражение |
| BACKEND_* | Неподдержанная семантика или mapping |
| ATTACK_* | Ошибки snapshot или связи ATT&CK |
| IO_* | Недоступный вход/выход |

При batch-обработке собирать ошибки независимых правил, но возвращать ненулевой exit code при любой ошибке. Для провалившегося правила не выпускать запрос. Писать output атомарно; существующий файл не перезаписывать без явного флага. stdout предназначен для результата, stderr — для текстовой диагностики. Точные коды будут зафиксированы тестами CLI.
