# Участие в разработке

## Начало работы

Прочитайте README.md, ARCHITECTURE.md, ROADMAP.md и SECURITY.md. Перед изменениями проверьте `git status --short --branch`, текущую ветку и diff. Соблюдайте применимые AGENTS.md, если они появятся. CLAUDE.md не нужен для обычной работы; не читайте его без причины. Существующие файлы не удаляйте.

Создавайте отдельную ветку для задачи. Для крупных изменений сначала опишите проблему, границы поддержки Sigma и критерии приёмки в issue. Не помещайте конфиденциальные детали в публичные issues и PR.

## Безопасные входные данные

Используйте полностью синтетические правила и события. Не добавляйте production-логи, персональные данные, токены, пароли, внутренние hostnames/адреса, tenant IDs или конфигурации заказчиков. Даже тестовые secrets обозначайте очевидными placeholders. Новые fixtures должны иметь описанное происхождение и лицензию. Входной YAML никогда не исполняется.

## Требования к изменениям

- Парсер: положительный и отрицательный тест, позиции диагностики и проверки лимитов.
- Валидация: код ошибки и пример исправления без раскрытия исходного значения.
- Backend: capabilities, dialect/version, mapping и golden-пары, поведенческие edge cases.
- ATT&CK: фиксированная версия snapshot, provenance/digest, unknown/deprecated/revoked случаи.
- CLI: stdout/stderr, exit codes, существующий output и batch failures.
- Зависимости: обоснование, совместимая лицензия, фиксированные версии и обновление lock-файла.

Golden обновляется только после review объяснения изменения семантики или формата. Не принимайте изменение snapshot только потому, что оно делает тест зелёным. Не выдавайте локальные fixtures за измерение эффективности в реальной инфраструктуре.

## Документация и проверка

README.md описывает текущие возможности; INSTALL.md — реально работающую установку; ROADMAP.md — незавершённые этапы; CHANGELOG.md — фактические изменения. Меняя контракт, обновляйте ARCHITECTURE.md. Сохраняйте LICENSE и SECURITY.md; не меняйте условия лицензии без отдельного решения.

Сейчас функционального кода и unit/golden tests нет; доступен только `python3 scripts/smoke.py` для runtime и документов: не заявляйте, что unit/golden tests проходят. Проверяйте Markdown-ссылки, согласованность статуса и `git diff --check`. После появления runtime команды форматирования, lint и тестов должны быть закреплены здесь и в CI.

PR должен описывать проблему, поведение после изменения, проверку и ограничения. Перед отправкой просмотрите staged diff на чувствительные данные. Уязвимости обсуждайте приватно по SECURITY.md, а не в публичном issue.
